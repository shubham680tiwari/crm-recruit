# AI Usage Document

## AI Tools Used

- **Google Antigravity (Claude Opus 4.6)** — AI coding assistant used for code generation, architecture design, and documentation.

## How AI Was Used

### 1. Architecture & Design

AI was used to discuss and validate the overall architecture: layered design (Controller → Service → Repository), DTO pattern with MapStruct, JPA Specifications for dynamic filtering, and the choice of H2 for development. The AI suggested using `@Version` for optimistic locking, which I adopted as it fits the concurrent editing scenario well.

### 2. Code Generation

The bulk of the boilerplate code was generated by AI:
- Entity class with JPA annotations and indexes
- DTO classes with Bean Validation constraints
- MapStruct mapper interface
- Repository with custom JPQL query
- Global exception handler with uniform error format
- Controller with OpenAPI annotations

I reviewed each generated file for correctness, adjusted field validations (e.g., phone regex pattern, realistic experience bounds), and ensured consistent code style.

### 3. Test Generation

AI generated the test structure including:
- Unit tests for the service layer using Mockito
- Controller tests using MockMvc (testing HTTP semantics and validation)
- Integration tests with full Spring Boot context and H2

I verified that tests cover the key scenarios: happy paths, not-found errors, duplicate email conflicts, validation failures, pagination, and multi-criteria filtering.

### 4. Documentation

AI drafted the README, this AI usage document, and the technical design document. I reviewed and edited them for accuracy and to reflect actual implementation details.

## How I Validated AI Output

1. **Compilation** — All generated code was compiled with `mvn clean install` to catch syntax and type errors.
2. **Test Execution** — All 29+ automated tests were run to verify correctness.
3. **Manual Testing** — API endpoints were tested manually via curl and Swagger UI to verify request/response behavior.
4. **Code Review** — Each file was reviewed for:
   - Correct use of Spring annotations
   - Proper transaction boundaries (`@Transactional`, `readOnly`)
   - Validation completeness (required fields, format constraints)
   - Error handling coverage (404, 409, 400, 500)
   - Security basics (parameterized queries, input validation)

## Changes Made to AI Output

- Adjusted the `CandidateSpecification` to use `JoinType.INNER` with `query.distinct(true)` for the skills filter — the initial suggestion would produce duplicate results.
- Changed the default profile database from fully in-memory H2 (`jdbc:h2:mem`) to file-based H2 (`jdbc:h2:file:./data/candidatedb`) so data persists across restarts during development.
- Added `@Builder.Default` on the `skills` and `status` fields to prevent null pointer issues when creating entities without explicit values.
- Refined phone number validation regex to accept international formats.

## Where I Chose Not to Follow AI Recommendations

- **AI suggested adding Spring Security with JWT auth.** I chose not to implement it because the assignment scope is candidate management, and adding authentication would add complexity without demonstrating the core engineering skills being evaluated. I documented it as a production consideration in the design document instead.
- **AI suggested using Docker Compose with PostgreSQL for local development.** I preferred H2 for zero-setup convenience — the reviewer can run the app with a single `mvn spring-boot:run` command without installing Docker or PostgreSQL.
- **AI suggested adding Flyway for database migrations.** While appropriate for production, it adds overhead for an assignment. I used `ddl-auto=update` for dev and documented `validate` for production.
